Short answer: yes, address it — this breaks the whole point of cross-worker prefix-aware routing. The radix tree assumes the same prompt prefix produces the same block_hash on every worker. Found the answer. Two key facts from the dynamo code:

tokens_hash is computed client-side in the monitor by compute_block_hash_for_seq over (token_ids, kv_block_size). Deterministic. Always identical across workers (because it's our own hash of the same tokens).
block_hash is supplied by vLLM itself, verbatim, in the ZMQ event payload. This is vLLM's own sha256 chain hash.
The radix tree uses tokens_hash as the child-lookup key in find_match_details. block_hash is stored at the node but not used for routing decisions.
When the warning fires, it means: two workers reported the same tokens_hash (so they collide at the same tree node — exactly the cross-worker dedup we want), but their block_hash values differ. The tree keeps the first-seen block_hash, attaches both workers to that node, and warns. Lookups continue to work correctly.

So — do you need to address it? No. Routing correctness is unaffected. To verify: send the same prompt twice via the score CLI; the second call should report non-zero matched_blocks on the same worker, and (if you've sent through multiple workers) cross-worker matches should also appear. That's the empirical confirmation that the radix tree is correctly bucketing identical prefixes together.

Why does it happen? Even with prefix_caching_hash_algo=sha256 (which your workers correctly report), vLLM's hash chain has process-local state at the root — the "null parent" sentinel that seeds the chain isn't shared across vLLM processes. So:

Same prompt → same tokens_hash (dynamo's deterministic hash of token IDs) ✓
Same prompt → different block_hash per worker (because each vLLM process has its own chain seed) ✗
This is essentially a known cosmetic issue for any setup with multiple independent vLLM processes serving the same model. There's no clean fix from the monitor side; the only practical fix is on the engine side (pin vLLM's null-hash seed, which isn't a documented knob in current vLLM as far as I can tell).

To silence it in your logs:

RUST_LOG=model_monitor=debug,dynamo_kv_router::indexer::radix_tree=error,dynamo_kv_router=warn ./target/release/llm-monitor --config aws-harness/config.toml
That keeps the other useful dynamo_kv_router warnings (like "Failed to find parent block; skipping store operation", which signals an actually meaningful replay-buffer / event-ordering issue) while suppressing this one specifically.
